## 模块 1：大模型基础与 Agent 机制

### 1.1 LLM 是概率性系统 [已检索 + 通用]

- LLM 按 token 生成，每次生成是从概率分布里采样，同一个输入两次可能不同输出。
- 三件套必讲：`token`（计价与上下文的基本单位，约等于 0.75 个英文单词，中文约 1 字≈1~2 token）、`上下文窗口`（单次能"看见"的 token 上限）、`temperature`（越低越确定、越高越发散）。
- 幻觉（hallucination）不是"bug"而是机制固有：模型在优化"下一个 token 像不像"，不是"这句话是不是真的"。
- **PM 视角的关键结论**：确定性软件可以说"输入 A 一定输出 B"，AI 产品只能说"输入 A 大概率输出接近 B"。所有产品设计、验收标准、指标都要围绕这个前提展开。
- 用于：m1-l1

### 1.2 RAG（检索增强生成）[已检索]

- 机制：用户提问 → 检索外部知识库相关片段 → 把片段塞进 prompt → 模型基于片段+问题生成答案。
- 解决的问题：模型不知道的私有/最新知识；降低幻觉；可引用来源。
- **关键失败模式**：检索层错了，模型会基于错误片段"自信地答错"。RAG 把错误从"模型编的"变成"检索给的"，**并没有消除错误，只是换了出错位置**。这是 PM 必须理解的点——它意味着 RAG 产品要单独评测"检索质量"，不能只看最终答案。
- 数据新鲜度是 RAG 的最大卖点之一（更新知识库 ≠ 重新训练模型）。
- 用于：m1-l2

### 1.3 提示 / RAG / 微调 三级阶梯 [已检索]

决策顺序（"最便宜的先试"）：

| 层级 | 改什么 | 什么时候用 | 代价 |
|---|---|---|---|
| Prompt engineering | 改「你问什么」 | 永远第一步：格式、语气、人设、结构化推理 | 几乎为零，分钟级迭代 |
| RAG | 改「模型能看见什么」 | 模型缺私有/最新/公司内部知识 | 要建检索管线，有运维复杂度 |
| Fine-tuning | 改「模型默认怎么表现」 | 行为一致性/风格/窄领域高精度，且提示+RAG 补不上 | 训练贵、要高质量标注数据、基座升级要重来 |

- 核心口诀（写进课程）：「**RAG 改模型知道什么，微调改模型默认怎么表现**」；「**变化的知识放进上下文检索，必须恒定的行为放进权重微调**」。
- 反例（重要考点）：**拿微调去灌"随时会变的事实"** —— 更新要重训，且用新事实微调反而会加重幻觉。
- 降本场景：高频高量（如 >20 万次/月）时，微调一个小模型可能比每次调大模型便宜很多——这是**成本驱动**的微调，不是能力驱动的。
- 用于：m1-l3

### 1.4 Function Calling / Tool Use [已检索]

- 模型不再只"生成文字"，而是输出一个结构化的"我要调用某工具、参数是这些"的指令，由应用层真正执行，再把结果喂回模型。
- PM 视角：模型本身不"操作数据库/发邮件/改状态"，**真正执行动作的是你的后端**，所以权限、幂等、审计都在应用层，不在模型层。这是"AI 能干什么"和"AI 被允许干什么"的分界。
- 用于：m1-l4

### 1.5 Agent Loop（ReAct）、MCP、Context Engineering [已检索]

- **ReAct 循环**：Thought（想下一步）→ Action（调工具）→ Observation（看结果）→ 回到 Thought。多步任务靠这个循环一步步推进。
- 产品风险：必须设**迭代上限**防死循环；每轮循环烧 token（成本）和延迟；需要"什么时候停/什么时候交给人"的规则。
- **MCP（Model Context Protocol）**：用统一协议把工具从 agent 里解耦，同一套工具可被不同 agent 框架复用（本地走 stdio、远程走 HTTP）。
- **Context Engineering**：管理喂给模型的上下文（prompt、工具 schema、历史观察），防止 token 膨胀、保证模型看到最相关最省的信息。
- 用于：m1-l5（用 TripGenie 对话助手做贯穿例子）

## 模块 2：模型选型与推理经济学

### 2.1 成本 / 延迟 / 准确率三角 [已检索]

- 没有"最好的模型"，只有"这个场景最合适的模型"。三者在多数时候互相拉扯：
  - 更强 = 更贵、通常更慢；
  - 更快更便宜 = 往往在复杂推理上吃亏。
- 分层选型：简单任务（分类、抽取、改写）用便宜小模型；高难度推理/高风险用前沿大模型；中间用路由（router）按请求复杂度分流。
- 用于：m2-l1

### 2.2 按 token 计价的算术 [已检索]

- 定价单位：每百万 token，分 input / output 两个价；**output 通常是 input 的 2–10 倍**（因为输出是逐 token 生成的，更贵）。
- 长上下文可能有溢价（超过某长度后单价上升）。
- 缓存（prompt caching）约省 90%；批处理（batch）约省 50%。
- **关键：应算"每答案成本（cost per answer）"而不是"每 token 成本"** —— 要算上重试、工具调用、上下文膨胀。
- 课程量化练习设计：给一张模型价格表（合成），给一个典型请求的 input/output token 量、重试率、日均请求量，让学员用 Python 算出：
  - 单次答案成本
  - 每千次/每日成本
  - 两种模型/两种参数配置下的月成本差
  - 结论：什么情况下该换模型
- 用于：m2-l2（code 练习）

### 2.3 延迟指标 [已检索]

- 不能只看平均延迟，要看 **p50 / p95 / p99**（尾部行为才是用户真正会碰到的痛点）。
- 拆解：首 token 时间（TTFT，用户"感觉等了多久"）vs 总生成时间（全部输出完）。
- **流式输出（streaming）改善的是"体感延迟"**，不改变总时长——这是 PM 常用来救体验的低成本手段。
- 用于：m2-l3

### 2.4 降本手段与"不该用大模型" [已检索 + 通用]

- 降本四板斧：模型路由、prompt 缓存、批处理、换小模型/微调小模型。
- 不该上大模型的任务：**确定性规则能覆盖的**（如固定格式校验）、**零容错且无人工兜底的**、**没有反馈信号无法改进的**、**数据不足的**。
- 用于：m2-l4

## 模块 3：Prompt 系统化工程

### 3.1 Prompt 结构 [已检索]

- R-I-C-C-E：Role（角色）/ Instructions（指令）/ Context（上下文）/ Constraints（约束）/ Examples（示例）。
- 好 prompt 的特征：目标明确、输出格式可验证、边界条件写清、给出正反例。
- 用于：m3-l1

### 3.2 few-shot 设计 [通用 + 已检索]

- few-shot = 在 prompt 里给几个「输入→输出」示例，教模型按这个模式作答。
- 陷阱：示例数量不是越多越好（占上下文、可能过拟合到示例的偶然特征）；示例顺序影响结果；**示例本身有偏见会传染**（只给"都是正面"的例子，模型也会倾向正面）。
- 什么时候需要 few-shot：输出格式复杂/有隐含规则/零样本效果不稳定时。
- 用于：m3-l2

### 3.3 Prompt 版本化与回归 [已检索]

- 把 prompt 当代码资产：每个版本有唯一 ID、改动原因、关联模型与参数、评测结果。
- 有评测闸门：改 prompt 必须跑回归评测，防止"修了一个问题、坏了另外三个"（silent regression）。
- 三轮调优记录表要记：版本号 / 改了什么 / 为什么改 / 用哪些样本验证 / 前后指标对比。
- 用于：m3-l3（writing 练习）

## 模块 4：评测体系设计

### 4.1 为什么 AI 产品必须建评测 [已检索]

- 传统验收："这个按钮点了会跳转"——确定性可测。
- AI 验收："这句话回答得好不好"——同一输入不同输出，必须用**数据集 + 评分标准 + 阈值**来定义"合格"。
- 用于：m4-l1

### 4.2 rubric 设计 [已检索]

- rubric = 分维度、分档位、每档有定义和示例的评分细则。
- 好的 rubric：每档可操作（换个人打也大致一致）、有正反例、维度正交（准确性/相关性/信任度/可操作性 这四维是课程默认框架）。
- 反例：只写"好/中/差"三档不写定义 → 人工之间都对不齐，更别说 LLM judge。
- 用于：m4-l2

### 4.3 golden set 建设 [已检索]

- 起点规模：200–500 条代表性样本（高价值决策场景可更多）。
- 来源：真实用户使用（尤其负反馈/BadCase）、边界样例、对抗样例（prompt injection、刁钻问法）。
- 纪律：**像代码一样版本化管理**，改数据集要有记录，否则评测分数不可比（测试集漂移会假装成模型变好/变坏）。
- 用于：m4-l3

### 4.4 LLM-as-Judge 与偏差 [已检索]

- 机制：用一个强模型按 rubric 给另一个模型的输出打分，可规模化、成本低于全人工。
- **三类已知偏差**：长度偏差（偏爱长答案）、位置偏差（成对比较时偏爱某位置）、同族偏差（偏爱同家模型输出）→ 对策：明确 rubric、换不同家族当裁判、随机打乱位置。
- **人工对齐门槛**：与人工专家打分的对齐率要到 85–90% 才可大规模信任；且要**先验人工之间的一致性**。
- 运维：异步执行（不在请求链路上）、抽样而非全量、单独监控 judge 成本。
- 用于：m4-l4

### 4.5 Cohen's kappa 校准 [已检索]

- 公式：κ = (po − pe) / (1 − pe)，po = 观察一致率，pe = 随机一致率。
- 判读：κ ≥ 0.6 可接受（substantial 约 0.61–0.80），≥ 0.8 强（almost perfect ≥ 0.81）。
- **为什么不用裸一致率**：当某一类标签极其常见时（比如 95% 都是"合格"），随便全打"合格"也有 95% 一致率，但 κ 会很低。裸一致率会骗人。
- 流程：先算人工之间 κ（<0.6 说明 rubric 本身含糊，先修 rubric，别急着用 judge）→ 再算 judge vs 人工 κ → 迭代到接近人工之间水平。
- 用于：m4-l4（code 练习：给混淆矩阵，算 po、pe、κ，判断能否采用 judge）

### 4.6 离线好、线上差 [通用]

- 五种常见原因：
  1. **分布漂移**：线上用户的问法和评测集不一样。
  2. **评测集污染**：样本泄漏进训练数据 / 评测集被"针对优化"过（过拟合评测集）。
  3. **指标与业务脱节**：评测分高 ≠ 用户满意（比如答案更长但没帮助）。
  4. **体验成本被忽略**：答案对了但延迟太高、要等太久，用户不用。
  5. **用户行为改变**：上线后用户开始问更难的问题（选择性适应）。
- 用于：m4-l5

### 4.7 BadCase 闭环 [已检索]

- BadCase（真实负反馈）→ 归因分类 → 进回归评测集 → 每次改动复跑 → 防止"修了又坏"。
- 回归集要有维护说明：谁负责、多久更新、怎么防止"只加不退"导致无限膨胀。
- 用于：m4-l6（writing 练习）

## 模块 5：PRD 撰写

### 5.1 PRD 是什么 [已检索]

- PRD = 产品需求文档，核心作用是对齐"为什么要做、做成什么样、怎么算做完了"，减少研发/设计/数据/运营的理解偏差。
- 和方案文档的区别：PRD 说"要什么和为什么"，技术设计说"怎么做"。
- 用于：m5-l1

### 5.2 PRD 十二要素 [已检索]

1. 战略基础（背景、用户问题、与公司目标的对齐）
2. 目标（可衡量：做成之后什么变了）
3. 用户故事（谁、做什么、为什么）
4. 核心概念（术语与不变量，防语义漂移）
5. 范围与非目标（明确 out-of-scope，防蔓延）
6. 用户流程与入口（每个受影响的界面/触发点）
7. UI 状态（默认/加载/错误/空）
8. 埋点（上线前定义事件与属性）
9. 技术护栏 / 非功能要求（性能、安全、可扩展）
10. **AI 专属需求**（见 5.3）
11. 风险与缓解
12. 发布计划、约束、开放问题

三处最常见写法坑：① 目标写成"提升用户体验"（不可衡量）；② 只写主流程不写失败/空状态；③ 不写非目标导致范围失控。
- 用于：m5-l2

### 5.3 AI 专属章节 [已检索]

必须写清：
- AI 具体承担哪些任务、**自主度分级**（只建议 / 建议+人确认 / 自动执行）
- 输入、输出、上下文、数据源
- 护栏：输入护栏、输出护栏、检索护栏、工具调用护栏
- **失败模式与兜底行为**、**人工升级路径**（什么情况转人、谁能覆盖）
- 何时需要人工审核/批准
- 为什么必须用 AI（而不是确定性规则）
- 用于：m5-l3

### 5.4 验收标准 vs 成功指标 [已检索]

- 验收标准（acceptance criteria）= 发布**闸门**，pass/fail，按功能区组织。
- 成功指标（success metrics）= 上线后观察，带目标值和观察窗口。
- AI 的验收标准不能是"点一下能跑"，必须是：**eval 数据集 + 质量阈值 + 延迟阈值 + 成本阈值**。
- 用于：m5-l4

### 5.5 PRD writing 练习 [设计]

- 给一个场景（TripGenie 某类对话改进 / 或通用 AI 客服场景）。
- 要求用模板写出：背景与问题、目标用户、范围与非目标、AI 专属需求、验收标准、成功指标、风险。
- 自检清单逐项勾选；给一份范文对照。
- 用于：m5-l5

## 模块 6：Roadmap、指标、优先级、实验

### 6.1 指标体系分层 [已检索]

七层：业务指标（收入/效率）、采纳指标（DAU/MAU/激活）、任务指标（完成率/自动化率）、AI 质量指标（正确率/幻觉率）、安全指标、系统指标（延迟/可用性）、经济指标（每任务 token/每次交互成本）。

- **北极星指标**要同时含"AI 有效时带来的价值"和"AI 失效时带来的成本"。例：copilot 用"借助 AI 完成任务的用户数"；工单系统用"无需人工升级即解决的工单占比"。
- 反例：拿"模型准确率"当北极星——那是模型指标，不是产品指标。
- 用于：m6-l1

### 6.2 漏斗与 activation [已检索]

- activation = 用户第一次真正用上 AI 价值的时刻（不是"注册"也不是"点击"）。
- 对 AI 产品，activation 常是"第一次成功完成一个任务且结果被接受"。
- 用于：m6-l2

### 6.3 RICE 与 AI 额外关卡 [已检索]

- RICE = (Reach × Impact × Confidence) / Effort。
- AI 特征额外过三关：安全/合规、HITL 设计、prompt injection 风险。
- writing 练习：给 6 个候选功能，算 RICE 并排一版季度 Roadmap，写清排序理由与依赖。
- 用于：m6-l3（writing）

### 6.4 A/B 实验样本量 [已检索]

- 四要素：基线转化率 p0、最小可检测效应 MDE、显著性 α（常用 0.05，双侧 z≈1.96）、功效 1−β（常用 0.8，z≈0.842）。
- 常用近似公式（每组样本量）：

  n = (z_{α/2} + z_β)² × [p1(1−p1) + p2(1−p2)] / (p1−p2)²

  其中 p1 = p0，p2 = p0 + MDE。
- 还要把需求样本量 ÷ 日流量 = 最少跑几天；且至少覆盖整周（防周内效应）。
- code 练习：给基线、MDE、日流量，算每组样本量和最少实验天数，判断"两周够不够"。
- 用于：m6-l4（code 练习）

### 6.5 PMF 与 kill/scale [通用]

- 验证信号：留存、主动复用、推荐意愿、付费意愿。
- kill/scale 标准：事先写下"到什么信号就加码、到什么信号就停"，避免沉没成本。
- 用于：m6-l5

## 模块 7：商业化、增长、风险

### 7.1 单位经济 [通用]

- 三种模式：订阅（可预测但可能被重用户亏钱）、按量（与成本对齐但用户焦虑）、混合（基础订阅+超量计费）。
- 关键算术：每用户月收入 vs 每用户月推理成本 → 毛利。重用户可能把毛利吃穿。
- 用于：m7-l1

### 7.2 增长 [通用]

- PLG：产品自己就是获客渠道；AI 产品的 PLG 常卡在"第一次成功体验"。
- 信任是增长的前置条件：一次严重幻觉可能毁掉口碑。
- 用于：m7-l2

### 7.3 风险与护栏 [已检索]

- prompt injection：用户输入里藏指令劫持模型行为；对策：输入隔离、工具最小权限、输出校验、HITL。
- 越权工具调用：给 agent 的能力越大，越需要权限边界与确认。
- 人类在环三种设计：规则闸（满足条件必须人审）、风险闸（风险分高转人）、抽检（按比例抽查）。
- 用于：m7-l3

### 7.4 什么不该用 AI [已检索 + 通用]

- 五类红灯：确定性规则可解、零容错无兜底、无数据基础、无反馈闭环、合规禁止。
- 用于：m7-l4

## 模块 8：作品集与面试

### 8.1 作品集四段式 [已检索]

- 问题（真实用户痛点、你怎么发现的）→ 方法（为什么这么做、为什么用 AI）→ 证据（怎么验证效果、诚实报告失败与迭代）→ 结果（量化影响）。
- 高价值信号：能界定模糊问题、懂模型行为（不止会写 prompt）、交付过真实用户用过的产物。
- 用于：m8-l1

### 8.2 Vibe coding 做 Demo [通用]

- 范围要小：打通一个完整任务闭环，而不是功能大而全。
- 要能讲清背后 agent 链路（RAG / 工具调用），以及哪些是自己做的、哪些借力 AI 编程。
- 用于：m8-l2

### 8.3 产品 sense 拆解 [已检索]

- 框架：用户 → 问题（现状怎么解决、痛点） → 方案（为什么 AI） → 指标（成功怎么衡量）。
- 致命失分：一上来就谈模型/方案，假设"AI 就是答案"。
- 10 分钟讲完的结构。
- writing 练习：给一个场景现场拆解。
- 用于：m8-l3（writing）

### 8.4 AI 权衡题与行为题 [已检索 + 通用]

- 权衡题：准确率 vs 延迟 vs 成本、模型选型、什么不该用 AI；答题要"先约束后选择"。
- 行为题：如"模型效果不达预期导致延期"——考你如何管理模型风险、如何与技术团队对齐权衡。
- 转岗叙事：不虚构 PM title，卖点 = research-driven product partner（用研究定义方向、用评测证明效果）。
- 用于：m8-l4

### 8.5 对话设计作品 [通用]

- 组成：对话流程图、Prompt 库、语气策略、A/B 测试设计。
- 用于：m8-l5
